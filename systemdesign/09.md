When an application grows, a single server can’t handle all incoming traffic. So we add multiple servers, and to manage them properly, we introduce a Load Balancer.

Let’s see how a Load balancer actually distribute the request to multiple servers. 

A Load Balancer is not just a traffic funnel it’s a decision maker. To decide, it uses Algorithms. 

1. Static Algorithms:
These don't check if a server is dying or healthy. They just follow the rules.

* Round Robin:  
       How it works: Request 1 ->Server A. Request 2 ->Server B. Request 3 again to server A, request 4 again to server B and so on.
    ◦ Best for Simple setups where all servers are equally powerful.

* Weighted Round Robin:
    ◦ How it works: If Server A is a beast (16GB RAM) and Server B is weak (4GB), you tell the LB: "Send 4 people to A for every 1 person to B."
    ◦ Best for A mix of old and new hardware.

* IP Hash :
    ◦ How it works: It uses the user's IP to ensure User X always goes to Server A. Hence decides on the basis of IP
    ◦ Best for: Shopping carts. If you switch servers mid-session, your cart might vanish.

2. Dynamic Algorithms:
These are intelligent. They check the server's pulse before sending work.

* Least Connections: 
    ◦ How it works: Who has the fewest open connections right now? Send the new guy there.
    ◦ Best for Long sessions like Discord chats or WebSocket apps.

* Least Response Time: The speed demon.
    ◦ How it works: The LB pings everyone. Whoever replies fastest gets the job.
    ◦ Best for Gaming or trading apps where lag kills.

* Resource-Based: The doctor.
    ◦ How it works: An agent on the server reports back: "I'm at 90% CPU, don't send more!" The LB listens and routes traffic elsewhere.
    ◦ Best for Heavy, complex applications.

These are some standard industry level algorithms used by a LB internally to distribute network traffic.
